# Data Relay Link vs Data Relay Control

The products share the Data Relay name and the idea of **relaying only what is needed**, but they solve different problems at different layers.

| Question | Data Relay Link | Data Relay Control |
| --- | --- | --- |
| Main job | Secure, controlled connectivity | Enterprise data collection, processing, and delivery |
| What it relays | **Network connections** | **Application data and events** |
| Typical direction | External → internal and internal → approved external | Enterprise sources → one or many destinations |
| Typical inputs | Remote administrators, private/isolated hosts | SaaS, API, databases, files/logs, devices/IoT |
| Typical outputs | Selected internal services or approved Internet destinations | SIEM, XDR, Data Lake, SOAR, Analytics, Custom Apps |
| Main control | Which host/service may connect | Which records/fields go where and in what form |
| Example functions | Remote access, approved egress, access control, connection logs | Filtering, selection, transformation, masking/removal, protection, route-specific delivery |
| Main benefit | Safer and simpler restricted-network connectivity | Collect once, reduce duplicate integrations, deliver destination-specific data |
| Product dependency | None | None |
| Detailed docs | [link.datarelay.run](https://link.datarelay.run) | [control.datarelay.run](https://control.datarelay.run) |

## Choose Data Relay Link when

- an external administrator/support engineer must reach selected services inside a private or isolated network;
- a closed/restricted network host needs access only to approved external services;
- you want to reduce repeated VPN, NAT, firewall, proxy, or Squid configuration changes;
- the problem is fundamentally **network reachability and connection control**.

## Choose Data Relay Control when

- application data/events must be collected from enterprise sources;
- one source must feed multiple destinations;
- different destinations need different filtering, transformation, masking/removal, or protection;
- you want centralized visibility and management of data delivery;
- the problem is fundamentally **data integration, processing, and distribution**.

<Note>
  An organization can use either or both products, but using both does not make them one integrated system. Evaluate and deploy each product for its own problem domain.
</Note>
