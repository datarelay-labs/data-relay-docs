# Data Relay Link vs Data Relay Control

두 제품은 Data Relay라는 이름과 **필요한 것만 선택적으로 Relay한다**는 생각을 공유하지만, 서로 다른 Layer의 문제를 해결합니다.

| 질문 | Data Relay Link | Data Relay Control |
| --- | --- | --- |
| 핵심 역할 | 안전하고 통제된 Connectivity | Enterprise Data 수집·처리·전달 |
| Relay 대상 | **Network Connection** | **Application Data / Event** |
| 대표 방향 | 외부 → 내부, 내부 → 허용된 외부 | Enterprise Source → 하나 이상의 Destination |
| 대표 입력 | 원격 관리자, 사설/폐쇄망 Host | SaaS, API, Database, File/Log, Device/IoT |
| 대표 출력 | 선택된 내부 서비스 또는 허용된 외부 목적지 | SIEM, XDR, Data Lake, SOAR, Analytics, Custom App |
| 핵심 제어 | 어떤 Host/Service에 연결할 수 있는가 | 어떤 Record/Field를 어디로 어떤 형태로 보낼 것인가 |
| 대표 기능 | Remote Access, 승인된 Egress, 접근 제어, 접속 기록 | Filtering, Selection, Transformation, Masking/Removal, Protection, Route별 Delivery |
| 핵심 효과 | 제한망 연결을 더 안전하고 단순하게 | 한 번 수집하고 중복 Integration을 줄이며 목적지별 데이터 전달 |
| 제품 의존성 | 없음 | 없음 |
| 상세 문서 | [link.datarelay.run](https://link.datarelay.run) | [control.datarelay.run](https://control.datarelay.run) |

## Data Relay Link가 맞는 경우

- 외부 관리자/지원 엔지니어가 사설망이나 폐쇄망의 선택된 서비스에 접속해야 함
- 폐쇄망/제한망 Host가 승인된 외부 서비스에만 접속해야 함
- VPN, NAT, 방화벽, Proxy, Squid 설정 변경을 반복하는 부담을 줄이고 싶음
- 핵심 문제가 **Network Reachability와 Connection Control**임

## Data Relay Control이 맞는 경우

- Enterprise Source에서 Application Data/Event를 수집해야 함
- 하나의 Source를 여러 Destination으로 보내야 함
- Destination별로 다른 Filtering, Transformation, Masking/Removal, Protection이 필요함
- Data Delivery의 Visibility와 Management를 중앙화하고 싶음
- 핵심 문제가 **Data Integration, Processing, Distribution**임

<Note>
  두 요구사항이 모두 있으면 두 제품을 각각 사용할 수 있지만, 두 제품을 함께 사용한다고 하나의 통합 시스템이 되는 것은 아닙니다. 각 제품을 자신의 문제 영역에 맞게 독립적으로 평가하고 배포합니다.
</Note>
